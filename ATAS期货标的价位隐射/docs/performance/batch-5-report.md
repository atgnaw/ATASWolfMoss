## IB 源码模块

原本位于 Pro 的 IB 传输、期权适配器及基础模型已移动到
`shared/WolfMoss.IB`，通过 `WolfMoss.IB.props` 源内编译。
不是复制两套长期维护的实现，也不是多个插件依赖同一个运行时业务 DLL。

模块分为 Transport 与可选 Options。传输层提供 SDK 加载、回调桥接、Socket／Reader 构造、
异步限速发送、共享请求等待、请求 ID、身份排他登记和诊断计数。
期权层提供现有合约发现、连接池、订阅租约、generic tick 合并及行情线预算。
OI 日缓存、Flow 聚合、交易时段业务、ATAS 绘制与性能记录仍留在 Pro。

模块不引用 ATAS／WPF／Nightwatch。实际增加两个独立控制台消费者：

- ConsumerA：包含期权层。
- ConsumerB：仅传输层，可作为另一类 IB 适配器的编译起点。

它们可分别构建、独立执行，也可在同一进程与 Pro 同时加载。
未来插件无需安装本 Pro，但需自己的程序集／指标名、Client ID、设置和存储目录。
详细接入、许可与所有权约定见 [源码复用指南](../../shared/WolfMoss.IB/README.md)。

为保护现有枚举／设置序列化，保留原 `WolfMoss.ATAS.PriceMapping` 命名空间；
这不是 ATAS 依赖。不同插件之间不互传私有编译的模型或官方 SDK 对象。

## 同时加载的实际问题及修复

以前依赖加载器会优先搜索进程中同名的 CSharpAPI／Protobuf。
另一个插件如果先加载不同版本，就可能让本插件绑定错误的 API 或类型。
现在每个消费程序集从自己的嵌入资源加载 SDK／Protobuf，使用私有加载上下文，
不再复用全局同名程序集，不添加全局 AssemblyResolve 处理器。

新增多消费者测试还发现：仅隔离 SDK 不足够。
`DispatchProxy` 按代理基类的上下文复用动态代理程序集；当所有代理基类都在默认上下文时，
第二份同名 SDK 的 EWrapper 可能与第一份串用，导致第二个 EClientSocket 构造失败。
此问题已在离线测试中复现并修复：为每份 SDK 缓存一个私有代理基类桥接，
并在同一上下文生成代理。多个消费者的 Socket 构造与回调路由现在都通过。
原因可对照 [.NET DispatchProxyGenerator 实现](https://github.com/dotnet/runtime/blob/main/src/libraries/System.Reflection.DispatchProxy/src/System/Reflection/DispatchProxyGenerator.cs)。

SDK／代理按消费程序集首次需要时加载；重连复用，不每次重新生成。
私有上下文为非可回收，随宿主进程存续。这有每插件一份 SDK 的常驻开销，
不能解释为零成本、安全沙箱或支持热卸载。

## 连接身份与互不干扰的边界

- 相同插件内：同一 host/port/client_id 继续共享连接与订阅；最后一位消费者释放才断开。
- 不同插件：各自持有连接池、请求 ID、回调、订阅和取消状态；不共享连接对象。
- 本模块不同源码副本仅共享一个进程级身份排他登记：相同端点和 Client ID 不能同时连接。
- 常见 loopback 别名统一；任意 DNS 别名不猜测。其他进程或未用本模块的插件由 Gateway 检测。
- 重复身份与 IB 326 明确显示 `CLIENT_ID_IN_USE`，不自动递增 ID、不接管已有连接。
- 请求 ID 是连接内原子编号，耗尽报错、不溢出；不是 IB order_id。

实际运行时仍需给其他插件不同 Client ID，例如 Pro 2210、其他插件 2310。
不同 Client ID 不增加账户总行情额度，也不能隔离 Gateway 重启、账号掉线或上游限流。
本批没有做跨插件的账户级预算中心；各插件应分配自己的预算，为其他使用者留空间。
连接约定见 [IBKR Connections](https://interactivebrokers.github.io/tws-api/connection.html)。

未来历史／交易插件可以复用底层，但历史 pacing、订单 ID／状态恢复、授权与风险控制
仍需另立业务层。本 Pro 不增加历史查询、账户或订单操作，不配置 Master Client ID。

## 显示列扩展

新增统一注册入口 `FuturesReferencePriceAxisDealerHeatmapIndicator.Columns.cs`，
每列注册：种类、可见开关、快照读取、绘制、悬停、状态文本以及数据源生命周期。
注册顺序保持 Heatmap → GEX → OI → Flow；现货映射轴仍在最左侧。

- 布局通过不可变 `DealerColumnCatalog` 计算列宽、位置与保留宽度。
- 绘制、悬停、状态面板不再分别写四套启用分支。
- 两个 Nightwatch 列共享一个生命周期；OI／Flow 共享一个 IB 生命周期，初始化和释放各执行一次。
- 快照引用数组按注册列数管理，新增列自动参与状态缓存失效判断。
- 关闭列不占空间；映射／十字线穿过所有启用列；状态面板继续位于最右侧。
- 注册使用静态委托，不每帧构造委托／描述对象。元数据复制只在注册时发生。
- 状态缓存命中复用已有文字；失效时额外复制一份很小的快照引用数组，不复制行情内容。

以后新增列仍需实现其设置、数据逻辑、绘制并添加 kind／visibility 及一条注册，
但不必改写多处分支布局。它是编译期注册机制，不是动态脚本插件系统。
本批未增加新显示列，也未改变固定／Rolling 桶、ATM、迟到基线或 OI 确认语义。

## 手动验收与对比

只部署 Pro 的 `src/FuturesReferencePriceAxis.DealerHeatmap/bin/Release/FuturesReferencePriceAxis.DealerHeatmap.dll`。
不要把两个 ReuseProbe 测试程序集复制到 ATAS。按原方式完全退出 ATAS 后替换，
便于清除上一版本常驻 SDK；原先保存的 DLL 可用于回退和性能对比。

1. 先独立运行本 Pro：检查原模板、各列开关、列序、同宽、状态与悬停。
2. 开启 OI／Flow，确认 Gateway 使用设置的 Client ID；关闭一列不影响另一列。
   所有图表均关闭两项后，对应连接和行情线应释放，Nightwatch 继续正常。
3. 开盘后使用与旧版本一致的图表数、品种、21 档、时间桶、诊断模式和观察时长。
   比较 PERF 绘制／快照／回调平均与 P95、共享发送与取消、行情线、受监测循环，
   并观察 ATAS CPU／内存和长期增长。不要只拿空闲周末对比活跃盘中。
4. 将来第二插件完成后，用独立 Client ID 和保守预算一起测试：
   单独运行各自正常；关闭／重开其一不令另一方丢连接或取消订阅。
   故意相同 ID 时应该明确冲突，而不是静默换 ID；改回不同 ID 后恢复。
5. 若 Gateway／账号本身断开，两个插件都可能受影响，这不属于本地隔离保证。

本批完成后暂停。历史持久化接口／数据库等后续工作等待用户确认，不在本批实施。
